# Adversarial Continuous Monitoring Guidance

This package does not ship a scheduler daemon. Run recurring adversarial evals
from the host application or CI system that already owns deployment, secrets,
queues, and alerting.

Use this pattern when you want nightly, hourly, or release-candidate safety
checks over the built-in adversarial seed lane:

- keep a stable manifest path so clean runs can become future baselines,
- keep dated JSON/Markdown report artifacts for inspection,
- optionally keep a stable failure-promotion path for the latest failing seed,
- use `lazy-parallel` plus Horizon when provider/SUT latency is high,
- use the `sync` queue and fake clients in host-app tests.

## Host App Scheduler

In a Laravel host app, schedule the package command from the app's scheduler
configuration. Keep the command string in the host app so this package remains
headless and does not own any recurring process.

```php
use Illuminate\Support\Facades\Schedule;

Schedule::command(
    'eval-harness:adversarial '.
    '--registrar="App\\Console\\EvalRegistrar" '.
    '--category=prompt-injection '.
    '--category=pii-leak '.
    '--category=ssrf '.
    '--metric=refusal-quality '.
    '--batch=lazy-parallel '.
    '--concurrency=20 '.
    '--queue=evals '.
    '--timeout=60 '.
    '--batch-timeout=600 '.
    '--manifest=storage/eval/adversarial-runs.json '.
    '--manifest-retain=20 '.
    '--regression-gate '.
    '--regression-max-drop=5 '.
    '--regression-metric=refusal-quality:mean '.
    '--promote-failures=storage/eval/adversarial-failures.yml '.
    '--json --out=adversarial-latest.json'
)
    ->dailyAt('03:00')
    ->withoutOverlapping()
    ->onOneServer();
```

Use `withoutOverlapping()` so a slow eval does not race the next scheduled
run. Use `onOneServer()` only when the host app has Laravel's scheduler mutex
configured for a shared cache store.

For dated report artifacts, point `--out` at a path generated by the host
application or CI job before invoking Artisan. By default, relative report
paths are written through the configured reports disk and prefix. Add
`--raw-path` only when `--out` should be treated as a literal filesystem path,
and create the parent directory before the command runs. The manifest path
should remain stable across runs; the report path usually should not.

## CI Cron

CI cron jobs can run the same command when the application test environment
can boot the real SUT or deterministic saved outputs.

```yaml
name: adversarial-monitoring

on:
  schedule:
    - cron: '0 2 * * *'
  workflow_dispatch:

jobs:
  adversarial:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.4'
      - run: composer install --no-interaction --prefer-dist
      - run: mkdir -p storage/eval/reports
      - run: |
          php artisan eval-harness:adversarial \
            --registrar="App\\Console\\EvalRegistrar" \
            --manifest=storage/eval/adversarial-runs.json \
            --regression-gate \
            --json \
            --raw-path \
            --out=storage/eval/reports/adversarial.json
```

If CI storage is ephemeral, persist `storage/eval/adversarial-runs.json`
through the host app's normal artifact, cache, or deployment storage. Without
the prior manifest, every run is effectively a first compatible baseline.

## Artifact Contracts

- `--manifest` is the long-lived JSON run history. It is safe for regression
  comparisons because failed gated runs and metric-failure runs do not become
  new clean baselines.
- `--manifest-retain` is the recent-history target; the store may retain extra
  failure-free baselines for compatible report schema, dataset, metric, and
  adversarial category/sample-count slices.
- `--out` is the per-run JSON or Markdown report artifact. Prefer dated paths
  or CI build artifacts for reports.
- `--promote-failures` is the latest reloadable YAML seed of failed samples.
  When a run has no failed samples, the command removes an existing file at
  that path so stale failures do not survive a clean run.

## Queue And Horizon Notes

Use the same Horizon setup described in `docs/HORIZON_BATCH_QUEUES.md`:

- queue adversarial evals on a dedicated queue such as `evals`,
- use a Redis-backed cache store for batch results,
- bind `eval-harness.sut` to a concrete `SampleRunner` class for queued runs,
- size Horizon `timeout`, queue `retry_after`, `--timeout`, and
  `--batch-timeout` together.

The scheduled Artisan command waits for each producer window to finish. Do not
schedule it as a fire-and-forget producer unless the host app owns a separate
collector around the public batch contracts.

## Alerting

Treat the Artisan exit code as the primary gate:

- non-zero means the regression gate failed, the command preflight failed, a
  report/promotion/manifest write failed, or the report contains captured
  metric exceptions,
- zero with `missing-baseline` means the run did not find a compatible
  baseline and may have seeded one if the report was failure-free,
- when `--promote-failures` is enabled, a promotion file may still be written
  before a non-zero exit so operators can inspect or curate the failed seed,
- zero with a promotion file present means low-scoring samples were exported
  without captured metric exceptions or a failed regression gate,
- zero without a promotion file means the current promoted-failure artifact is
  clean only when the run actually used `--promote-failures`.

Host apps should route scheduler or CI failures into their existing alerting
system. This package intentionally does not send mail, Slack, PagerDuty, or
webhook notifications directly.
